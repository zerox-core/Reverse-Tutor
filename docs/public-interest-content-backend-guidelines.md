# 公益内容与挑战更新：后端开发注意事项

移动端 Canonical HTTP 契约见：`docs/contracts/openapi-online-v1.yaml`。本文件负责实现与运维约束；路径、字段和错误结构以 Canonical 契约为准。

## 1. 目标

为首页公益内容、每日文章和挑战更新提供低带宽、低存储、可持续维护的后端能力。

核心原则：

- 服务端保存内容和配置，不承担高频动画资源传输。
- 图片进入对象存储和 CDN，不写入 SQLite，也不长期保存在应用服务器硬盘。
- 动效模板和常用插画素材随客户端发布，每日内容只下发文字和模板配置。
- 首页先取轻量清单，正文和大图仅在用户打开文章时加载。

## 2. MVP 范围

第一阶段仅实现：

- 公益内容草稿、定时发布、发布和下线。
- 首页内容排序。
- Markdown 正文。
- 插画模板选择和对话文字配置。
- 一张可选封面图。
- 首页清单接口和文章详情接口。
- 版本、ETag、客户端缓存和资源清理。

第一阶段不实现：

- 富文本所见即所得编辑器。
- 视频、GIF 和任意动画文件上传。
- 实时推送和高频轮询。
- 复杂推荐算法。
- 多人协同编辑和版本合并。

## 3. 数据模型

SQLite 只保存结构化数据和文本。建议字段：

```text
public_content
- id
- slug
- content_type          # public_interest | challenge | announcement
- title
- summary
- body_markdown
- illustration_template
- illustration_config_json
- cover_asset_url
- publisher_name
- status                # draft | scheduled | published | offline
- sort_order
- publish_at
- offline_at
- content_version
- created_at
- updated_at
```

首页清单不要包含完整正文，只返回：

```json
{
  "version": 28,
  "updatedAtEpochMillis": 1783857000000,
  "items": [
    {
      "id": "public-028",
      "slug": "verify-before-opening-links",
      "type": "public_interest",
      "title": "别让陌生链接替你做决定",
      "summary": "三个对话，识别常见网络诈骗",
      "illustrationTemplate": "dialogue-security-01",
      "illustrationConfig": {
        "dialogues": ["这个链接安全吗？", "先核对来源，再决定是否打开。"]
      },
      "publishedAtEpochMillis": 1783814400000,
      "contentVersion": 2
    }
  ],
  "nextCursor": null
}
```

## 4. API 约定

建议保留以下接口：

```text
GET  /api/v1/content/feed
GET  /api/v1/content/{slug}
POST /api/admin/v1/content
PUT  /api/admin/v1/content/{id}
POST /api/admin/v1/content/{id}/publish
POST /api/admin/v1/content/{id}/offline
```

要求：

- `feed` 支持 `ETag` 和 `If-None-Match`。
- 内容没有更新时返回 `304 Not Modified`。
- 详情接口返回 `contentVersion`，客户端按版本更新缓存。
- 管理接口必须鉴权，普通客户端不能调用发布和下线接口。
- 定时发布任务必须幂等，重复执行不能重复创建内容。
- 下线内容从首页清单移除，但保留元数据，避免历史记录失效。

## 5. 插画与动效

每日内容不得上传 GIF、视频或大型 Lottie 文件作为首页动效。

推荐方式：

- 客户端内置简笔插画角色、图案和动效模板。
- 后端只下发模板 ID、对话、配色和可选参数。
- 同一套模板可以组合不同公益主题。
- 客户端开启“减少动态效果”时切换为静态状态。
- 新内容首次展示可播放一次短动效，之后降低动效强度。

只有无法通过模板表达的内容，才上传静态封面图。

## 6. 图片与对象存储

- 图片上传到 OSS、S3、R2 或同类对象存储。
- 正式资源不得保存在应用服务器本地目录。
- 数据库只记录资源 URL、哈希、尺寸和 MIME 类型。
- 上传后生成 WebP 或 AVIF，不保留无业务价值的超大原图。
- 文件名使用内容哈希，避免重复上传和缓存失效。
- 首页缩略图最大宽度约 `320px`，单张目标小于 `40KB`。
- 正文图片最大宽度约 `960px`，单张目标小于 `150KB`。
- 每篇文章建议不超过 `3-5` 张正文图片。
- 未被内容引用的资源进入待清理状态，保留观察期后删除。

## 7. CDN 与缓存

- 静态资源使用内容哈希 URL，并设置长期不可变缓存。
- 首页清单使用短缓存和 ETag，不使用永久缓存。
- 文章正文按 `content_version` 缓存。
- 客户端启动时检查一次，后台每 `6-12` 小时最多更新一次。
- 客户端只预加载当前轮播项和下一项。
- 已读文章和图片使用本地 LRU 缓存，建议上限 `20-50MB`。
- 应用切到后台后停止轮播和非必要请求。

## 8. 发布流程

```text
创建草稿
-> 编辑标题、摘要、正文和插画配置
-> 预览手机端首页与文章页
-> 设置发布时间和首页顺序
-> 发布
-> 清单版本递增并刷新 CDN
-> 客户端下次检查时增量更新
```

发布前必须检查：

- 标题和摘要在手机宽度下不会溢出。
- 插画模板 ID 在当前客户端版本中存在。
- 图片尺寸和体积符合限制。
- 发布时间、时区和排序正确。
- 正文链接有效。
- 下线时间没有早于发布时间。

## 9. 监控与清理

至少记录：

- 首页清单请求量和 `304` 命中率。
- 文章详情请求量。
- CDN 命中率和资源流量。
- 对象存储总容量。
- 发布失败和定时任务失败。
- 找不到插画模板或资源的客户端错误。

建议每月执行：

- 清理无引用资源。
- 检查异常大图。
- 检查长期草稿和过期内容。
- 复核缓存命中率和带宽费用。
- 更新客户端支持的插画模板列表。

## 10. 前后端契约

后端变更以下内容前必须先更新 `docs/contracts/` 并通知前端：

- `content_type`、`status` 或字段名称。
- 插画模板 ID 和配置格式。
- Markdown 扩展语法。
- 首页排序和轮播规则。
- 缓存版本、ETag 或下线行为。
- 图片尺寸、格式或 CDN 域名。

前端必须处理：

- 清单请求失败时继续展示本地缓存。
- 新模板无法识别时使用静态默认插画。
- 图片加载失败时显示占位状态。
- 内容被下线时退出详情页并给出说明。
- “减少动态效果”和离线状态。

## 11. 字体资源与系统字体回退

字体渲染、系统字体选择和缺字回退属于客户端职责。后端不得根据华为、Android 版本或用户主题字体返回不同正文内容，也不得把手机没有安装某款字体视为接口错误。

实现约束：

- `Noto Sans SC` 是设计校准字体，不是服务端运行依赖。客户端可按 `system sans -> HarmonyOS Sans SC -> Noto Sans CJK SC -> sans-serif` 回退；回退只允许改变视觉度量，不改变业务数据。
- 用户输入、LLM 回复、列表、按钮、通知和实时状态属于动态文本。后端只返回 UTF-8 文本，不返回字体文件、本地字体路径或强制字体名。
- 公益标题、剧情章节和挑战主题如需排版提示，只允许下发稳定的语义角色；是否增加 `typographyRole` 必须先在 `docs/contracts/` 冻结枚举、未知值回退和客户端版本兼容规则。
- 未知或客户端不支持的语义角色必须降级到默认 UI/内容字体，不能导致内容接口失败、重复请求或阻塞发布。
- 用户输入和 LLM 内容不得依赖字符子集字体。生僻字、繁体字、标点和 Emoji 的缺字回退由客户端处理，不通过后端改写原文规避。
- 字体默认随客户端版本发布。公益 Feed、文章详情和挑战接口不得重复下发完整字体文件，避免增加带宽、缓存复杂度和内容首屏延迟。
- 如果未来确需在线字体，必须使用对象存储和 CDN，并提供内容哈希 URL、字体版本、SHA-256、MIME、文件大小、许可证标识和可用回退；字体不得写入数据库正文或长期保存在应用服务器硬盘。
- 仅静态艺术字应随封面或插画资源发布，同时保留可访问的纯文本字段。静态资源加载失败时客户端显示普通字体文本，不重试下载同一字体来阻塞内容展示。
- 字体来源、版本和许可证必须进入资产清单；OFL 字体随客户端或静态资源分发时仍需保留对应许可证文件。

关联客户端契约：`docs/contracts/mobile-typography-tuning.md`。

## 12. “后端”关键词触发复核

后续需求或讨论中出现“后端”时，先提醒并复核本文件，重点确认：

1. 内容模型是否新增或修改字段。
2. API 路径和响应结构是否变化。
3. 插画模板与客户端版本是否兼容。
4. 图片体积、对象存储和 CDN 策略是否仍适用。
5. ETag、缓存时间和增量更新规则是否需要调整。
6. 发布、下线、排序和定时任务是否覆盖新需求。
7. 前端是否需要同步更新类型、状态和错误处理。
8. 是否新增字体语义角色或在线字体资源；是否仍只传语义和静态资源元数据，而不是强制字体名或字体文件。

如果需求会改变以上任一项，应先更新本文件，再开始后端实现。
