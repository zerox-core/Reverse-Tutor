# 反转家教「限时挑战」需求规格（v1.0 定稿）

> **摘要**：本文是「限时挑战」活动方向的需求规格定稿，由 v0.1 讨论稿经决策点拍板后落成。结论：系统骨架（在线 API、数据模型、端上 UI 四态）已建成并空置，本期交付**运营配置最小链路（管理 API）+ 首期中文活动内容**，随后端上联调、灰度上线。7 个决策点全部按推荐项定案，见 §7。

- 版本：v1.0（2026-09-24 定稿）
- 上游：v0.1 讨论稿（飞书文档 <https://larkcommunity.feishu.cn/docx/JaUkdR5DloP2clx5awxcZJjenue>）
- 关联：V1 全量计划社区线 L4；公益内容后端指南（docs/public-interest-content-backend-guidelines.md）

## 1. 背景与定位

「限时挑战」由原先的「每周挑战」更名而来——运营节奏无法保证每周颁布新任务，因此定位为**不定期发布的限时活动**：有明确的起止时间，过期关闭，下一期何时来不承诺固定周期。

在产品版图中的位置：V1 全量计划（docs/V1-DEVELOPMENT-PLAN.md）社区线 L4 的组成部分，原文为「首页：官方公告/更新内容/活动卡片/公益广告位（第一版手动配置，挑战活动手动搓一版）」，切片标记为 v1。即**第一版运营侧手动配置被计划明确接受**，不要求自动化排期。

与后续「监控面板 / key 分发」的关系：挑战活动 v1 不依赖注册与 key 分发体系，跑在现有匿名账户（`anonymous_accounts`，设备维度）上即可；未来额度奖励类挑战可作为与 key 分发的联动点，属后话。

## 2. 目标与非目标

**目标**（按优先级）

1. 拉留存：给用户一个「今天回来打开 App」的理由，每日任务形态天然制造回访动机；
2. 引导核心行为：挑战任务挂在会话模板上（`session_template_id`），把活动流量导向会话算法这个唯一大方向；
3. 制造社区氛围：排行榜提供轻量攀比动机，为后续社区线（L1-L5）探路。

**非目标（v1 明确不做）**

- 实物 / 代币 / 现金类奖励；
- 用户自创建挑战（UGC）；
- 评论、点赞等社交互动；
- 固定周期的自动排期（每周/每月自动生成）；
- 推送通知系统（挑战提醒依赖用户主动进 App，锁屏推送属 V1 计划另一条线）。

## 3. 角色与核心场景

**用户侧**（匿名账户，一台设备一个身份）

1. 首页挑战面板发现活动 → 进入详情页（介绍、天数、每日任务、起止时间、排行榜）；
2. 点击加入 → 每日完成当天任务（进入挂接的会话模板完成学习会话）→ 进度+1；
3. 中途可退出；完成全部天数进入完成态；活动到期关闭。

**运营侧**（你本人，v1 手动）

1. 撰写活动内容（标题、介绍、每日任务 Markdown、会话模板参数）；
2. 通过管理 API 创建活动、配置起止时间与规则参数，发布上架；到期关闭或提前下线。

## 4. 现有基础盘点（已实现的骨架）

以下均已实现并有测试覆盖，本规格以此为基础，不重复建设：

- **数据模型**（online_db）：`activities`（slug/标题/介绍/总天数 `total_days`/起止时间/四态 `state`：scheduled、active、closed、offline/规则版本 `rule_version`/会话模板 `session_template_id`）、`activity_tasks`（按 `day_number` 的每日任务，含 `task_markdown` 与阶段目标 `stage_goal`）、`activity_participations`（joined、pending_sync、completed、left 四态，进度与乐观锁 `revision`）、`activity_progress_events`（幂等键去重的进度事件流）；
- **在线 API**（/api/v1）：活动列表、详情、加入、进度上报、退出、排行榜，写接口带设备校验与幂等；
- **存储层**：`SqlAlchemyActivityStore.create_activity`（含每日任务，单事务写入）已存在；`list_activities` 支持按状态过滤；
- **端上**（Android）：`HttpOnlineApi` + 仓库层已接线，挑战详情页四态（加载/可加入/离线/不可用）+ 中文兜底文案，排行榜拉取失败保留上次快照；
- **种子数据**：1 个示例活动「Python 21 天挑战」（21 天、需在线确认、允许离线延迟进度、挂会话模板 `challenge-python-21-days-v1`）；
- **契约**：进度默认单调递增（openapi 注明 unless the activity says otherwise），参与进度走 Room Outbox + FastAPI 双写，离线可攒进度后补。

**关键缺口（本期补齐）**

1. 运营配置链路为零：内容只能改种子代码（`catalog_seed.py`）→ 本期补最小管理 API（D5）；
2. 首期活动的真实内容未设计（现有 21 天 Python 挑战是英文示例数据）→ 本期新写中文主题（D6）；
3. 排行榜的展示名来源未定 → 系统生成（D7），端上展示规则随联调落地。

## 5. 功能需求（用户端）

| 编号 | 需求 | 现状 | 缺口 |
|---|---|---|---|
| F1 | 首页挑战入口卡（有活动时展示，无活动时隐藏或兜底） | 面板已就位，LocalOnly 下显示离线兜底 | 接入真实在线地址后联调 |
| F2 | 活动详情（介绍、天数、每日任务列表、起止倒计时） | API 与 UI 已就位 | 每日任务列表的 UI 呈现需确认是否已渲染 `activity_tasks` |
| F3 | 加入 / 退出 | 已实现 | 无 |
| F4 | 每日进度上报（完成任务后进度+1，离线可攒后补） | 已实现（含幂等与延迟进度） | 与「完成一次会话」的自动联动需确认触发点 |
| F5 | 排行榜（进度排名、本人高亮） | 已实现 | 展示名按 D7 系统生成，联调时接线 |
| F6 | 完成态与到期态展示 | 状态机已支持 | 完成后的荣誉呈现（徽章/称号）按 D3 纯荣誉设计，随联调落地 |

## 6. 功能需求（运营端）

| 编号 | 需求 | 说明 | 本期结论 |
|---|---|---|---|
| B1 | 创建挑战活动（文案、天数、每日任务、起止时间、规则参数） | 管理 API：POST /api/admin/v1/activities | 本期实现 |
| B2 | 上架 / 关闭 / 下线（scheduled → active → closed；任意态 → offline） | 管理 API：POST /api/admin/v1/activities/{slug}/publish、/close、/offline | 本期实现 |
| B3 | 内容修订（`revision` / `rule_version` 递增） | 模型已支持 | 本期不做修订接口，改内容=下线旧活动+新建 |
| B4 | 视觉资产按公益内容指南约束：插画走客户端内置模板（后端只发模板 ID + 文案 + 配色），图片走 CDN 不进库，缩略图不超过 320px/40KB | 指南 §12 要求，凡涉后端先复核该文件 | 遵守 |

**管理 API 鉴权**：环境变量 `ONLINE_ADMIN_TOKEN` 配置静态管理令牌（≥32 字节随机串），请求头 `Authorization: Bearer <token>`，服务端用 `hmac.compare_digest` 恒定时间比较；未配置时管理接口整体 503，令牌错误 401。普通客户端不可调用（管理接口挂在独立路由前缀 /api/admin/v1，不走匿名会话鉴权）。

**状态机约束**：合法流转仅 `scheduled → active → closed` 与 `任意态 → offline`；非法流转返回 409。closed 为终态定格（见 D2）。

## 7. 决策记录（D1-D7 全部定案）

| 编号 | 议题 | 定案 | 说明 |
|---|---|---|---|
| D1 | 挑战形式 | **N 天每日任务型** | 沿用现有模型，零改动；累计目标型/一次性限时型以后再说 |
| D2 | 「限时」语义 | **closed 后一律冻结** | 到期关闭后新用户不可加入、进行中用户不可补进度，排行榜定格 |
| D3 | 奖励 | **纯荣誉** | 完成徽章/称号展示在活动页，不发任何实际权益；额度奖励等 key 分发体系上线后再议 |
| D4 | 断签规则 | **累计制（断签不算失败）** | 完成天数累计即可，与 `allows_deferred_progress` 离线延迟进度语义兼容 |
| D5 | 运营配置方式 | **补最小管理 API** | 创建 + 上下架 + 管理鉴权；活动是不定期运营动作，改种子很快成为负担，且管理 API 后续公益内容复用 |
| D6 | 首期活动内容 | **新中文主题** | 首期另起贴近反转家教定位的主题（候选：「21 天给 AI 讲懂一个知识点」），内容撰写为 M2 后续工作项 |
| D7 | 排行榜展示名 | **系统生成** | 形如「家教学员 + 尾号」，零摩擦；用户自取昵称以后再说 |

## 8. 非功能需求

- **离线优先**：进度上报必须离线可攒、恢复后补（已实现，Outbox 双写）；活动详情与排行榜允许展示缓存快照；
- **幂等**：所有写接口幂等（已实现，进度事件按操作键去重）；管理 API 创建按 slug 唯一约束天然幂等（重复 slug 409）；
- **数据量级**：单活动参与数百至数千量级，排行榜分页即可，无需特殊设计；
- **合规**：活动内容需过你本人审核后上架，v1 无 UGC 故无内容审核压力；
- **安全**：管理令牌只存在服务端环境变量，不进 APK、不进仓库；管理接口不暴露给公网匿名流量（部署层可再加 nginx 内网限制，属上线配置项）。
