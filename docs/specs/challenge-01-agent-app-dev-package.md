# 首期挑战知识包设计：教 AI 学会「落地 agent 应用开发」

> 版本 v0.1（骨架定稿，逐日任务全文待填充）。本文是知识包三件套（资料库 / AI 学生配置 / 对话策略）的设计母版，后续拆分为可被 app 加载的内容文件。父文档：challenge-activity-requirements.md。

## 1. 主题定位

- **一句话**：用户用 15 天把「如何从零落地一个 agent 应用」完整教给一个 AI 学生，教会 = 挑战完成。
- **学习者画像**：有基础编程能力、用过 LLM 应用但没独立落地过 agent 的开发者（大赛选手、学生开发者）。
- **为什么选这个主题**：边界清晰（有明确的「会/不会」判据）、误解点天然丰富（demo 派 vs 工程派的落差）、与用户自身的开发实践强相关（教的过程就是复盘）。

## 2. 概念地图（7 个模块 = AI 学生的 7 条掌握度维度）

| 模块 | 核心内容 | 「学会」的判据 |
|---|---|---|
| M1 场景与边界 | 什么任务适合 agent（开放、多步、需工具决策），什么该用固定 workflow；任务闭环=输入→产出→验收标准 | 学生能给一个具体场景正确归类 agent/workflow/普通 LLM 调用，并说出理由 |
| M2 Agent 核心循环 | 感知→规划→工具调用→观察→迭代；ReAct 与 plan-and-execute 两种范式；终止条件 | 学生能手画 loop 并指出每一步的输入输出；能说出 3 种终止条件 |
| M3 工具设计 | 工具描述写法、参数 schema、返回结构；工具数量控制；错误处理与幂等 | 学生能评审一个写差的工具定义并改对；知道工具超过一定数量会劣化选择 |
| M4 上下文工程 | 系统提示结构（角色/规则/边界/输出格式）；上下文预算与历史裁剪；会话内记忆 vs 长期记忆 | 学生能指出一份臃肿 prompt 的问题并重写；能给出上下文超预算时的 2 种压缩策略 |
| M5 可靠性与纠偏 | 任务分解；反思的边界（无外部验证的反思是空转）；人机回环时机；幻觉控制（grounding、引用来源） | 学生能说明「反思」什么时候有用什么时候浪费；能说出哪些动作必须停下来问人 |
| M6 评测与迭代 | eval 集构建（代表性 case + 边界 case）；指标（完成率/工具调用正确率/成本/延迟）；badcase 驱动迭代 | 学生能为一个 agent 设计 ≥20 条的 eval 集结构并说明分层理由 |
| M7 部署与运营 | 成本控制与模型分级（贵模型做难点、便宜模型做路由）；超时/重试/限流；监控指标与告警；灰度发布 | 学生能列出一个 agent 上线前 checklist 并解释每项防的是什么 |

## 3. 分天骨架（15 天，可调）

每模块 2 天：第 1 天「听课日」讲透概念，第 2 天「应用日」场景纠错；第 15 天综合验收。

- D1-D2：M1 场景与边界
- D3-D4：M2 核心循环
- D5-D6：M3 工具设计
- D7-D8：M4 上下文工程
- D9-D10：M5 可靠性与纠偏
- D11-D12：M6 评测与迭代
- D13-D14：M7 部署与运营
- D15：综合验收——AI 学生独立输出一份完整 agent 应用设计方案（含 loop、工具集、上下文策略、eval 集结构、上线 checklist），讲给「零基础第三者」听，用户按 checklist 评分

累计制打卡（D4 定案）：断签不算失败，完成天数即进度；每天预计 20-30 分钟。

## 4. 误解注入库（AI 学生的「学习障碍」设计，共 8 条）

每条 = 暴露时机 + 学生错误样例 + 期望的用户纠正 + 标准答案要点。被纠正（correction 证据）是掌握度增长的最大来源。

- **E1（M1，D1 末）**「agent 不就是给 LLM 写个好点的 prompt 吗」→ 期望纠正：agent 的本质是 loop + 工具 + 状态，prompt 只是其中一环。标准答案：M1/M2 讲义。
- **E2（M1，D2）**「我们那个定时拉数据再总结的流程也是 agent」→ 混淆固定编排与自主决策。判据：流程路径是否由模型在运行时决定。
- **E3（M3，D5 末）**「把能用的工具都给它，它自己会挑」→ 工具过多稀释注意力、选择劣化；经验法则：单 agent 工具保持个位数到十几个，超出就拆分或分层。
- **E4（M4，D7 末）**「上下文窗口这么大，全塞进去不就行了」→ 噪声稀释、成本爆炸、关键指令被淹没；正确做法：裁剪/摘要/分层注入。
- **E5（M5，D9 末）**「让它自己反思几遍就不会错了」→ 没有外部验证（工具结果、eval、人审）的反思是空转，反而放大自信幻觉。
- **E6（M6，D11 末）**「demo 能跑通就能上线了」→ demo 只证明 happy path；上线前必须有 eval 集、失败重试、成本与延迟预算。
- **E7（M7，D13）**「全用最贵的模型，效果肯定最好」→ 不懂模型分级与路由；简单分流/格式化任务用便宜模型，成本可差一个数量级。
- **E8（M7，D14）**「上线后出问题看日志就行」→ 无结构化监控（成功率/延迟分位/token 消耗/工具失败率）等于裸奔；日志是事后翻案，监控是实时发现。

## 5. AI 学生配置（对接现有掌握度/记忆算法）

```yaml
student:
  mastery_dimensions: [M1, M2, M3, M4, M5, M6, M7]  # 每条 0-1，初始 0
  evidence_weights:  # 沿用现有 EVIDENCE_SCORES
    explanation: 0.35        # 用户讲解（听课日主事件）
    retrieval: 0.55          # 学生准确复述
    correction: 0.90         # 用户纠正误解（应用日主事件）
    delayed_retrieval: 0.82  # 隔天仍记得（听课日开场抽查）
  misconception_injection:
    trigger: 对应模块 mastery 达到 0.3 且到设计暴露时机
    clear_when: 用户完成一次有效纠正（学生能复述正确版本）
  forgetting:
    # 具体函数数值待后端遗忘曲线定稿后替换（沿用现有阻塞项）
    rule: 隔天未互动的模块 mastery 按遗忘曲线回退，隔天开场抽查命中率同步下降
  mastery_gates:
    below_0.5: 回答含糊、主动犯该模块误解
    above_0.7: 能举一反三，仅保留 1 条深层误解留到综合验收
    complete_when: 全模块 ≥0.8 且 8 条误解全部清除
```

## 6. 对话策略（AI 学生行为脚本）

**听课日（每模块第 1 天）**
- 开场：抽查前一天的模块（delayed_retrieval 证据采集点），忘得多的话主动说「昨天那个我有点模糊了」。
- 听课中：认真听、分段复述要点、问澄清式问题（「所以 X 和 Y 的区别是…？」），问题深度随 mastery 上升。
- 收尾：按设计暴露当模块的浅层误解（E 库对应条目），等用户纠正。

**应用日（每模块第 2 天）**
- 开场：主动拿一个具体落地场景追问（「那如果工具调用超时了呢？」「用户输入乱来怎么办？」）。
- 中段：暴露该模块核心误解并坚持一轮（不用户一纠正就立刻改口，要求用户给出理由），被说服后复述正确版本。
- 收尾：学生总结「我今天学到的」，用户确认或补刀。

**综合验收日（D15）**
- 学生独立输出完整设计方案（第 3 节定义的产物），讲给「零基础第三者」听。
- 用户按 checklist 评分；仍有未清除误解的模块在此时做最后一次暴露。
- 评分结果回喂 mastery，决定挑战是否完成。

**人格基调**：好学、真诚、有主见但不抬杠；被纠正后要给「恍然大悟」的反馈而不是机械认错（风格红线另见 diary-persona-style 方法论，正式 prompt 在内容填充阶段编写）。

## 8. 与学生卡归并的关系

活动结束后，本知识包整体（modules + student.yaml + dialogue-policy.md）原样固化为一张「学生卡」，挂进创建会话窗口：任何用户一键创建「教 AI 学 agent 应用开发」的常驻会话。即知识包的内容格式从第一天起就按「学生卡可复用」的约束设计——不写死活动日期、排行榜等运营信息，运营层信息只存在活动实例上。
